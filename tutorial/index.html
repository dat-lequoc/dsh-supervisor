A hands-on course, from the ground up

Build an Always-On Supervisor Agent on DeepSeek Harness

Fifteen chapters that take you from “what is a plugin?” to a running 24/7 Main Agent that spawns, watches, steers, and kills worker subagents — built almost entirely out of parts the harness already ships. Every chapter ends with something you can test live in your own running dsh web.

The philosophy of this course

Your design documents (/root/dev/DESIGN.md and /root/dev/IMPLEMENTATION_PLAN.md) describe a supervisor built from a preset plus five custom plugins. This course deliberately takes a native-first path instead: we reuse and configure what the harness already ships, and we write custom code only where nothing native exists. That gets you to a working system dramatically faster, and — more importantly for learning — every native piece you configure is a piece you end up understanding.

Concretely, here is what the design wanted and what the harness already provides:

Supervisor needNative mechanism (already running in your dsh)Custom code?
Spawn a background workerThe subagent tool (continuable in-process child)No
Steer a running workersend_message — queues a correction as the child’s next turnNo
Kill a workerinterrupt_agent + never message it again (zero further token burn)No
Worker blocked on a questionThe child’s native report tool — wakes the parentNo
Wake when a worker finishesNative settle notice, delivered to the parent unconditionallyNo
Wake on a timer (patience / periodic check)schedule_create (an opt-in overlay: two config rows)No — config only
Track the locked goalThe goal tool + the web UI’s goal displayNo
Inspect what a worker didChildren are ordinary sessions in the web GUI, and ordinary JSONL files on diskNo
The supervisor personality & protocolAn agent preset — a YAML file you authorNo code — YAML + prose
Durable state (goal, notes, questions, changelog)Plain files in .agi/, written with the shell/fs tools every agent hasNo — convention only
Extra UI, trace files, a no-argument wait tool—Optional, chapter 13

So the “build” is: one preset you author + two schedule rows + a persona that encodes the protocol + a file convention. Everything else is understanding — which is the point.

Why native-first wins here

Custom machinery is code you must debug while also debugging your agent’s behavior. When the spawn/steer/kill/report loop is the harness’s own, a failure can only be in your prompt or your protocol — a much smaller search space. You can always add the custom extras later (chapter 13 shows exactly how, using a real out-of-tree plugin already installed on this machine as the template).

What you need

  • This machine, as it is: a dsh web already runs in the tmux session dsh, serving http://127.0.0.1:3080. Chapter 4 tours it.
  • The harness source checkout at /root/deepseek-harness (version 0.1.0-rc.7) — we read it constantly; we never modify it.
  • No TypeScript experience. Chapters carry TypeScript corner boxes that teach exactly the syntax you are looking at, when you are looking at it.

How each chapter works

  • Narrative first — concepts in prose, then the real code.
  • Cited code — every claim about the harness points at a file (and usually lines) in /root/deepseek-harness so you can verify it yourself. Code blocks are labeled CITED (exists in the repo — go read it) or YOURS (you will write/paste it).
  • Test it live — a green box at the end of every milestone with the exact steps and the expected observation. Do not continue until it passes; later chapters assume it.
  • Auto-grading — every milestone box names its grader: python3 /root/dev/tests/grade.py m0…m7 scores the durable evidence (preset files, patch rows, .agi/ state, session event logs) and exits 0/1 at the 90% bar. all runs m0–m6 in one report; doctor shows what it can see. Details: /root/dev/tests/README.md.

A note on your existing plan

IMPLEMENTATION_PLAN.md predates two things: the design’s own simplifications (S1–S4) and your decision to build native-first. Where this course and the plan disagree — custom agi-spawn vs. the shipped subagent tool, brief.md files vs. prompt-carried tasks, custom tabs vs. the shipped session views — this course reflects the current decision and says so in place. The plan remains useful as the reference for the “maximal” custom build, which chapter 13 revisits.
