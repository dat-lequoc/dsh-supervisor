Part I — Foundations

Anatomy of the harness

How a running dsh is assembled from layers, where sessions and agents live, what a “turn” actually is, and — most important for you — the two-plane rule that decides where every change belongs.

From nothing to a running product: layers

A running dsh is one big Cordis plugin tree, and that tree is composed at boot from ordered layers of patches applied to an empty list. Nothing is hardcoded; even “the product” is just the result of the layering: 

[]                                  ← the profile root: literally an empty list
 + @deepseek-ai/dsh-base            ← bundle: model adapters, tools, persistence,
 |                                     sandbox, subagent machinery, jobs, goals ...
 + @deepseek-ai/dsh-web-app         ← bundle: the browser application
 + @dsh-external/…-antigravity      ← bundle: a third-party plugin (installed here!)
 + profiles/web/cordis.patch.yml    ← YOUR profile patch layer (currently [])
 + ~/.dsh/cordis.patch.yml          ← home-level patch layer (if present)
 + --patch overlays                 ← command-line extras

Each concept, precisely:

  • A profile is a directory under $DSH_HOME/profiles/<name> holding a package.json (which bundles to stack, plus out-of-tree plugin dependencies) and your own cordis.patch.yml. Templates web and headless auto-initialize. (Source: packages/boot/app-boot/README.md, “Profiles”.)
  • A bundle is an npm package whose manifest declares "dsh": { "bundle": { "patch": "./cordis.patch.yml" } } — a distributable stack of config rows plus the code they mount.
  • A patch targets a row by id and replaces its whole config, or inserts new rows. Your profile’s patch file is watched live: edit it and the tree recomposes without a restart. (Same source: “Every profile boot keeps cordis.patch.yml live through watchUserPatches.”)

To see the fully composed tree your machine boots, there is a dump command (read-only, safe):

dsh --profile web --dump-config

Any row it prints can be replaced or disabled by a patch of your own. That single sentence is the harness’s entire “configuration API.”

The two planes: host composition vs. agent preset

Within that one process tree there are two kinds of place a plugin row can live, and choosing correctly is the most consequential decision you will make in this course. The Creator-mode skill states the criterion crisply:

Applied to your supervisor, once and for all:

ThingPlaneWhy
Supervisor persona, protocol textPresetOne session’s identity.
subagent, send_message, goal, todo toolsPreset rows (consuming host services)The preset decides whether this agent can call them; the machinery behind them is host-side.
The subagent registry + spawn/fork backendsHost (already there)Cross-session singleton; the browser queries it too.
Schedule service + tools (chapter 8)Host — two rows in your profile patchNot mounted by default; the shipped overlay adds it process-wide.
Any future custom plugin (chapter 13)Host, via profile dependencyMust observe every session / register process-wide capability.
The collision rule, now in full

A preset row that publishes a service without an isolate realm publishes it process-globally — and the second session mounting the preset collides with the first. The preset mounter rejects this instead of letting it blow up later, with a message that names the offending service. You met the fix in chapter 2 (wrap provider + consumers in one isolate group); the practical consequence is simpler: copy standard and keep its groups intact, and you inherit correct realms for free.

Agent presets: sessions choose their composition

A preset is a directory holding one agent.cordis.yml (the rows) and a preset.yml (display name, description). When you start a session in the web UI, you pick a preset; the roster mounts that composition for the session. Four ship with the deployment — standard, code, minimal, cordis (Creator mode) — living beside the install, and locally authored ones live under $DSH_HOME/.agent-presets/<id>/.

Why copy() instead of writing YAML from scratch

“A composition written from scratch usually forgets a group realm or a consumer row; a copy starts loadable” (editing-cordis-compositions skill). copy() also validates the id, lands the copy in the writable root wherever this deployment configured it, and rolls back on failure. Starting from standard is not laziness — it is the supported authoring path.

Inside a session: the log, the turn, the step

Now zoom into one running agent. Three nouns carry everything:

  • A session is an append-only log of durable events (user/message, assistant/message, tool/call, tool/result, turn/start…), plus a header (workspace cwd, parent lineage, creation time). It is literally a JSONL file on disk — you will open one in chapter 4.
  • A step is one model request plus the tool calls it makes.
  • A turn is zero or more steps: it opens when input is claimed and closes when nothing more is owed.

Two rules fall out of this that your supervisor design leans on:

  • Model-visible means logged. Anything that reaches a model request must be reconstructable from the session log — a runtime invariant. This is why a child agent’s entire behavior is inspectable after the fact from its log alone, which is your native replacement for the plan’s custom trace.log.
  • Input arrives through one inbox. An agent has a single FIFO inbox; every message — yours, a schedule reminder, a child’s report, a settle notice — becomes a turn in one observable order. “Sleep” is an empty inbox; “wake” is a delivery. There is no other scheduler.

The tool pipeline (where policy lives)

When a model asks to run a tool, the call travels a guarded pipeline — all waterfalls, all extensible by plugins: 

tools/pre-execute   → allow / deny / ask / transform / delay   (policy seat)
guards              → monotonic checks
tools/execute       → around-dispatch wrappers (timeouts live here)
tools/post-execute  → inspect or replace the result
tools/result        → the immutable outcome

You will not touch this pipeline in the native-first build, but you should know it exists for two reasons: it is where chapter 13’s optional tool-delay plugin would sit (docs/tool-execution-pipeline.md), and it explains the sandbox/approval prompts you see in the web UI — those are shipped pre-execute policies asking you to decide.
