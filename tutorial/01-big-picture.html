Part I — Foundations

The big picture

What you are building, why it is shaped this way, and the exact inventory of native parts you will assemble. No code yet — this chapter is the map you will navigate by for the next fourteen.

The product in one paragraph

A Main Agent runs as one long-lived chat session. When you give it a mission, it interviews you until the goal is unambiguous, writes the goal down, and gets your explicit confirmation — the one moment it is allowed to block on you. From then on it loops forever: it spawns a worker subagent with a task, sleeps, wakes when the worker finishes (or a timer fires, or you send a message), inspects what happened, and then steers, kills, or spawns the next unit of work. It never idles waiting for a human: if you don’t answer a question within a patience window, it records an assumption and moves on. Everything it knows lives in plain files on disk, so a crash or restart costs nothing.

The three roles

RoleWhat it isRealized as
Main Agent (supervisor) The one long-lived session. Plans, delegates, supervises, talks to you. It reads, searches, and verifies with its own tools — it understands what it orders and grades what comes back; only mutation is delegated. An agent preset named main-agent that you author in chapter 6, whose persona (chapter 7) encodes the whole protocol.
Dev Agent (worker) A disposable specialist spawned per unit of work: browser operator, researcher, implementer. Full tool access; installs whatever it needs at runtime. A native continuable background subagent — a real, durable session of its own — started by the shipped subagent tool (chapter 9). Its role travels in the spawn prompt.
You The goal-giver and the only authority for goal changes, credentials, and config. The person typing into the Main Agent’s chat in the web UI. All input flows through that one chat.

The heartbeat: sleep, wake, triage

The core of the system is a loop the Main Agent runs between your messages. It is worth internalizing now, because every later chapter builds a piece of it: 

ensure a locked GOAL exists            (chapter 7 — goal ceremony)
loop:
  plan the next unit of work
  spawn a worker with a complete task  (chapter 9 — native subagent tool)
  sleep                                (nothing to do: the turn simply ends)
  wake on ONE of:
    ├─ settle notice: the worker finished — native, unconditional  (chapter 9)
    ├─ report: the worker is blocked on a question — native        (chapter 9)
    ├─ schedule reminder: periodic check-in timer fired            (chapter 8)
    └─ user message: you typed something — that is steering
  triage:
    ├─ worker finished  → read its outcome, record progress, spawn next unit
    ├─ worker blocked   → answer via send_message, or ask you
    ├─ timer fired      → inspect the worker's session; on track → sleep again;
    │                     drifting → steer (send_message); poisoned → kill + respawn
    └─ you spoke        → your word overrides everything
Why “sleep” is free

In this harness an agent “running” means a turn is executing. Between turns an agent costs nothing — no polling loop, no tokens. So the Main Agent sleeps by simply ending its turn, and it wakes because the harness delivers something to its inbox: a settle notice, a child’s report, a schedule reminder, or your message. All four are native delivery mechanisms. The design documents call this “settle-or-timeout”; you get it without writing a scheduler.

The three verbs of supervision

The Main Agent manages workers with exactly three verbs, and all three are shipped tools you will meet in chapter 9:

VerbNative toolSemantics
spawnsubagent (continuable, background) Creates a durable child session with its own agent, delivers the task as its first message, returns a child id immediately.
steersend_message Queues a correction as the child’s next turn. A running child finishes its current turn first; an idle child wakes; a cold child is resumed from disk.
killinterrupt_agent + silence Stops the current turn. An un-messaged child does no further work and burns zero tokens. There is no “destroy” — the session remains on disk, inspectable.

And one verb belongs to the worker: report. A continuable child automatically gets a report tool; calling it delivers a message to the parent and (by default) wakes the parent’s turn. That is the blocked-question channel: the worker asks, stops, and the answer arrives as its next turn via send_message. Context preserved, no restart, no forking.

Files are the truth

The Main Agent’s chat context is a cache; the record is a directory of plain files in the target workspace, written as it goes. This is decision Q2c of your design and it survives the native-first rewrite untouched, because writing files needs no machinery — every agent already has shell and filesystem tools. 

.agi/
  config.json          # user-only knobs (patience minutes, wake minutes)
  GOAL.md              # written by the ceremony; never edited after locking
  GOAL_AMENDMENTS.md   # append-only, each entry user-confirmed
  NOTES.md             # the supervisor's free-form working memory
  progress.jsonl       # one JSON line per milestone/insight — your feed
  questions.jsonl      # question stack: pending → assumed/answered/withdrawn
  CHANGELOG.jsonl      # every spawn/steer/kill/assumption, one line each
  subagents/<id>/      # per-worker artifacts (outcome.md at minimum)

Chapter 7 turns this tree into a contract the persona enforces. Because they are plain files, your “UI” for them is anything that reads files — including the supervisor itself after a restart, which is the whole point.

Where this diverges from IMPLEMENTATION_PLAN.md

The plan (M2) builds four host plugins before anything works. We invert that: chapters 6–12 produce a complete working supervisor with zero host plugins, and chapter 13 shows how to add them if you find you want them. Two plan details are also superseded by the design’s own later amendments: workers get their task in the spawn prompt (no brief.md files — simplification S4), and there is no mandated wake ritual (S1) — native session persistence is the memory.

The two-plane rule (a preview)

One architectural idea governs every change you will make, so meet it early. A running harness composes plugins on two planes:

  • The host composition — one instance per process: registries, persistence, the sandbox, the model route, the subagent machinery. You touch it only through your profile’s patch file, and in this whole course you add exactly two rows to it (the schedule overlay).
  • An agent preset — what one session contributes: its tools, its persona, its prompt sections. This is where almost everything you author lives.

Chapter 3 develops this properly; chapter 6 applies it. If you ever wonder “where does this change go?”, the answer is: shared across sessions → host; one session’s capability → preset.

The first mission (eventually)

Your design names the acceptance mission: X.com growth automation — an open-ended, long-horizon task where workers operate a browser. We will not start there. Chapter 12’s acceptance run uses a deliberately boring goal (“produce a summary of a docs directory, delegating the work”) because a boring goal makes supervisor failures visible. The mission changes; the loop does not.
