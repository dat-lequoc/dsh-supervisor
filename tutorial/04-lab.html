Part I — Foundations

Your lab

A guided tour of the deployment you already have running — the process, the home directory, the sessions on disk, the web UI — and the short list of safety rules that keep it healthy while you experiment on it for the rest of this course.

The running process

A dsh web is already running on this machine inside a tmux session named dsh. Verify both, from any terminal: 

tmux ls                       # expect a session named: dsh
pgrep -af 'dsh web'           # expect: node /usr/local/bin/dsh web

It serves the web UI at http://127.0.0.1:3080 (the default — /root/deepseek-harness/README.md, “Run”). The left sidebar lists workspaces and their sessions; clicking a session shows its full conversation; the composer at the bottom talks to that session’s agent. When you start a new session you pick a preset — this picker is where your main-agent will appear after chapter 6.

Rule 1 — never start a second dsh against the same home

One $DSH_HOME, one process. A second dsh pointed at the same home corrupts live session logs. If you need the process restarted (rare in this course — the profile patch is hot-reloaded), do it inside the existing tmux session: 

tmux attach -t dsh        # Ctrl-C the running process, then: dsh web
                          # detach again with Ctrl-b d

The harness home: /root/.dsh

$DSH_HOME is unset on this machine, so the home defaults to ~/.dsh = /root/.dsh. Everything mutable lives here: 

/root/.dsh/
  profiles/web/
    package.json        ← which bundles this profile stacks (chapter 3)
    cordis.patch.yml    ← YOUR live-watched patch layer (currently: [])
  .agent-presets/       ← locally authored presets land here (chapter 6; empty now)
  sessions/             ← every session, as directories of JSONL logs
  settings.yaml         ← user settings (model routes etc.)
  .credentials.yaml     ← managed credentials
  storages/             ← small JSON caches (session projections, workspaces)

Three of these you will touch in this course, and only three:

  • profiles/web/cordis.patch.yml — chapter 8 adds the schedule overlay rows here.
  • .agent-presets/ — chapter 6 creates main-agent/ here (via the roster, not by hand).
  • sessions/ — read-only for you, but very instructive. Next section.

Sessions on disk — your free trace viewer

Chapter 3 claimed a session is “literally a JSONL file on disk.” Prove it to yourself. Sessions are grouped by workspace directory (the path with slashes turned into dashes): 

ls /root/.dsh/sessions/
# --root-dev--   --root-agi-testbed--   ...one directory per workspace

ls /root/.dsh/sessions/--root-dev--/
# session-ab70d480-...  one directory per session

# peek at one (each line is one durable event):
head -3 /root/.dsh/sessions/--root-dev--/session-*/events.jsonl 2>/dev/null \
  || find /root/.dsh/sessions/--root-dev-- -name '*.jsonl' | head -3

Open any of those files and you will recognize the vocabulary from chapter 3: turn/start, user/message, tool/call, tool/result, assistant/message, turn/end — one JSON object per line, append-only. Two consequences for your supervisor:

  • Worker inspection is grep. When the Main Agent wants to know what a worker has been doing, it can read the worker’s session log with the same shell tools it already has. No custom trace plugin required — this is the native-first replacement for the plan’s subagent-trace.
  • The web UI shows the same thing, rendered. Every child session appears in the sidebar like any other session, with its full conversation and tool calls. Your “Subagents tab” already exists; it is called the session list.
Test it live — read a real session log
  1. In the web UI, open any existing session and note roughly what happened in it.
  2. Find its file: grep -rl "some distinctive phrase from that chat" /root/.dsh/sessions/ | head -1
  3. grep -c 'tool/call' <that file> — count its tool calls; skim one with grep -m1 'tool/call' <file> | head -c 400.

Expected: the JSONL mirrors the rendered conversation event for event. When this feels obvious, you understand the harness’s single most important data structure.

The workspace for this course

Agents run in a workspace (the session’s cwd). Your supervisor is portable — all its state lives in <workspace>/.agi/ — so pick a scratch workspace for the build and testing chapters. Create it now: 

mkdir -p /root/agi-lab
cd /root/agi-lab && git init -q .   # optional, but lets you diff .agi/ changes

In the web UI, “new session” lets you choose this directory as the workspace. Everything the supervisor and its workers write lands under it. (Old experiments live in /root/agi-final, /root/agi-testbed, etc. — earlier attempts at this same system. Feel free to read their .agi/ trees for flavor; we start clean.)

The safety rules

All of them, in one place. They come from the shipped skills and the deployment’s own comments, not from caution theater:

RuleWhy
Never edit the shipped presets or the harness checkout. The agent-presets directory beside the install and /root/deepseek-harness are read-only for you. Copy, then edit the copy. An upgrade overwrites the install; corrupting the cordis preset disables Creator mode itself. (editing-cordis-compositions, “Off-limits”.)
Never start a second dsh on the same $DSH_HOME. Corrupts live session logs.
Host-plane changes go in profiles/web/cordis.patch.yml, nowhere else. Mind the YAML: duplicate row ids are fatal at compose time. It is the one live-watched, user-owned layer; mistakes are undoable by reverting the file.
Treat Creator-mode sessions like shell access. The cordis preset’s own header says so: its tools evaluate model-written JavaScript against the live runtime. (apps/cli/config/agent-presets/cordis/agent.cordis.yml, “TRUST”.)
Back up before big edits: cp /root/.dsh/profiles/web/cordis.patch.yml{,.bak} A broken patch layer leaves the last good tree running, but you want the easy way back.

Meet the API key reality

Model calls need credentials, which this deployment already has configured (/root/.dsh/.credentials.yaml, plus whatever settings.yaml routes). You never hardcode keys anywhere in this course; if a model route ever fails, that file and the web UI’s Settings → Models page are where to look.

Your dashboard habits

Three habits worth forming now, since every later “Test it live” uses them:

  1. Watch the process: tmux attach -t dsh (read the server log; detach with Ctrl-b d). Mount errors, patch reload failures, and plugin crashes print here.
  2. Watch the tree: dsh --profile web --dump-config | grep -n <row-id> to confirm a row you added actually composes. (Run it from a normal shell; it does not boot a second server.)
  3. Watch the disk: ls -lt /root/.dsh/sessions/--root-agi-lab--/ | head to see sessions appear as you spawn workers.
Test it live — lab checklist

Before moving on, confirm all five:

  1. tmux ls shows dsh, and http://127.0.0.1:3080 loads.
  2. cat /root/.dsh/profiles/web/cordis.patch.yml prints [] (or your existing patches).
  3. ls /root/.dsh/.agent-presets/ is empty (your main-agent is not born yet).
  4. /root/agi-lab exists.
  5. You opened one session JSONL and recognized the event types.
