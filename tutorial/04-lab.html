Part I — Foundations

Your lab

A guided tour of the clean deployment you started on the setup page — the process, the home directory, the sessions on disk, the web UI — and the short list of safety rules that keep it healthy while you experiment on it for the rest of this course.

The running process

The setup page started one dsh web process. Verify that process and its HTTP endpoint from another terminal: 

pgrep -af 'dsh web'
curl -I http://127.0.0.1:3080/

It serves the web UI at http://127.0.0.1:3080 (the default — $HOME/src/deepseek-harness/README.md, “Run”). The left sidebar lists workspaces and their sessions; clicking a session shows its full conversation; the composer at the bottom talks to that session’s agent. When you start a new session you pick a preset — this picker is where your main-agent will appear after chapter 6.

Rule 1 — never start a second dsh against the same home

One $DSH_HOME, one process. A second dsh pointed at the same home corrupts live session logs. If you need the process restarted (rare in this course — the profile patch is hot-reloaded), return to the terminal running it, press Ctrl-C, wait for shutdown, and start it again in that same terminal: 

dsh web

The harness home: $HOME/.dsh

Unless you deliberately exported DSH_HOME, Harness defaults to $HOME/.dsh. This course uses that clean-machine default. Everything mutable lives here: 

$HOME/.dsh/
  profiles/web/
    package.json        ← which bundles this profile stacks (chapter 3)
    cordis.patch.yml    ← your live-watched override layer
  .agent-presets/       ← user-owned/package-installed presets land here (no main-agent yet)
  sessions/             ← every session, as directories of JSONL logs
  settings.yaml         ← user settings (model routes etc.)
  .credentials.yaml     ← managed credentials
  storages/             ← small JSON caches (session projections, workspaces)

Four of these matter directly in this course:

  • profiles/web/package.json — chapter 6's plugin command safely adds the supervisor dependency and bundle entry; do not hand-edit it.
  • profiles/web/cordis.patch.yml — normally untouched; it is only for explicit overrides.
  • .agent-presets/ — chapter 6's bundle setup creates main-agent/ here via the roster.
  • sessions/ — read-only for you, but very instructive. Next section.

Sessions on disk — your free trace viewer

Chapter 3 claimed a session is a logical JSONL log on disk. By default it is frame-compressed as session.jsonl.zstd. Sessions are grouped by workspace directory: 

find "$HOME/.dsh/sessions" -name 'session.jsonl.zstd' | head

LOG=$(find "$HOME/.dsh/sessions" -name 'session.jsonl.zstd' | head -1)
zstd -dc "$LOG" | head -3

Open any of those files and you will recognize the vocabulary from chapter 3: turn/start, user/message, tool/call, tool/result, assistant/message, turn/end — one JSON object per line, append-only. Two consequences for your supervisor:

  • Worker inspection is grep. When the Main Agent wants to know what a worker has been doing, it can read the worker’s session log with the same shell tools it already has. No custom trace plugin required — this is the native-first replacement for the plan’s subagent-trace.
  • The web UI shows the same thing, rendered. Every child session appears in the sidebar like any other session, with its full conversation and tool calls. Your “Subagents tab” already exists; it is called the session list.
Test it live — read a real session log
  1. In the web UI, open any existing session and note roughly what happened in it.
  2. Choose its session.jsonl.zstd file from the workspace directory shown above.
  3. zstd -dc <that-file> | grep -c 'tool/call' — count its tool calls; skim one with zstd -dc <that-file> | grep -m1 'tool/call' | head -c 400.

Expected: the JSONL mirrors the rendered conversation event for event. When this feels obvious, you understand the harness’s single most important data structure.

The workspace for this course

Agents run in a workspace (the session’s cwd). Your supervisor is portable — all its state lives in <workspace>/.agi/ — so pick a scratch workspace for the build and testing chapters. The setup page created it; verify it now: 

test -f "$HOME/agi-lab/.agi/config.json"
find "$HOME/agi-lab/.agi" -maxdepth 2 -type f -print
cd "$HOME/agi-lab" && git init -q .   # optional: makes state changes diffable

In the web UI, “new session” lets you choose this directory as the workspace. Everything the supervisor and its workers write lands under it. On the clean baseline there are no earlier supervisor experiments to rely on.

The safety rules

All of them, in one place. They come from the shipped skills and the deployment’s own comments, not from caution theater:

RuleWhy
Never edit the shipped presets or the harness checkout. The agent-presets directory beside the install and $HOME/src/deepseek-harness are read-only for you. Copy, then edit the copy. An upgrade overwrites the install; corrupting the cordis preset disables Creator mode itself. (editing-cordis-compositions, “Off-limits”.)
Never start a second dsh on the same $DSH_HOME. Corrupts live session logs.
Host-plane changes go in profiles/web/cordis.patch.yml, nowhere else. Mind the YAML: duplicate row ids are fatal at compose time. It is the one live-watched, user-owned layer; mistakes are undoable by reverting the file.
Treat Creator-mode sessions like shell access. The cordis preset’s own header says so: its tools evaluate model-written JavaScript against the live runtime. (apps/cli/config/agent-presets/cordis/agent.cordis.yml, “TRUST”.)
Back up before big edits: cp $HOME/.dsh/profiles/web/cordis.patch.yml{,.bak} A broken patch layer leaves the last good tree running, but you want the easy way back.

Meet the API key reality

Model calls need the route you configured on the setup page. Harness stores managed credentials and settings under $HOME/.dsh; you never hardcode keys in a preset, workspace, or tutorial command. If a route fails, return to Settings → Models and make a standard-session prompt succeed before debugging the supervisor.

Your dashboard habits

Three habits worth forming now, since every later “Test it live” uses them:

  1. Watch the process: keep the terminal running dsh web visible. Mount errors, patch reload failures, and plugin crashes print there.
  2. Watch the tree: dsh --profile web --dump-config | grep -n <row-id> to confirm a row you added actually composes. (Run it from a normal shell; it does not boot a second server.)
  3. Watch the disk: find "$HOME/.dsh/sessions" -maxdepth 2 -type f | tail to see session storage appear as you work.
