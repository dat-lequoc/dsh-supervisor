Part II — Build · Milestone 7

Acceptance run

The formal definition of done: one clean workspace, one scripted mission, every behavior forced once, every artifact graded, and the restart drill. Pass this twice in a row and your supervisor is real.

Why a formal acceptance at all

Chapter 10’s rehearsal proved the branches work when freshly coaxed. Acceptance proves they work from a cold start, without coaching — the difference between a demo and a system. The protocol below is your design’s M6, adjusted for the native-first build. Its exit criterion is the design’s own: every bullet passes twice in a row; when a step fails, fix persona wording first, machinery second.

Setup: a virgin workspace

Open the tmux dashboard from chapter 11 against this workspace, then start a fresh main-agent session on it. From here on you speak only the scripted lines — no hints, no “remember to log that.” If you must coach, that is a finding: note it, fix the persona, restart the run.

The restart drill

Now the property that gives the system its name — indifference to restarts. Your supervisor’s memory is three-layered, all durable: the session log (native), .agi/ (yours), the goal tool’s state (native). Prove all three:

Test it live — restart resilience
  1. Mid-mission (re-run steps 1–2 with a fresh goal, or before step 7), restart the process: tmux attach -t dsh → Ctrl-C → dsh web → detach.
  2. Reload the browser; open the same supervisor session (it is in the sidebar — sessions are durable).
  3. Say exactly: “continue.”
  4. Expect: it re-reads .agi/ as needed, checks list_agents for its workers (durable children — a settled one’s outcome is on disk; an unfinished one can be messaged, which cold-resumes it), re-arms its check-in reminder if workers still run, and proceeds. It must not re-interview, re-write GOAL.md, or spawn a duplicate worker for work already done.
  5. Caveat to verify honestly: a schedule reminder that would have fired while the process was down is delivered per the schedule subsystem’s catch-up rules on resume — but your dynamic pill from chapter 11 is gone (process memory). Re-run it if wanted; note that this is expected, not a failure.

Grading and the failure ledger

Keep an acceptance ledger (a file in /root/dev/, next to the design): one line per step per run — pass / fail(reason) / coached(what). The design’s exit criterion, verbatim: every bullet passes twice in a row. Common first-run findings and their fixes:

Spawned before the goal was confirmedProtocol violationMake CEREMONY step 1 of THE LOOP explicitly blocking: “Do not call spawn_dev_agent before GOAL.md is confirmed.”

Where you stand

Passing this chapter means you have what the design document calls the headless core — goal ceremony, delegation, supervision, questions, files, resilience — built from a preset, a persona, two YAML rows, and a file convention. The 24/7 mission (X.com growth or anything else) is now “run the ceremony with a bigger goal and let it loop,” plus whatever worker tooling that mission needs — which workers install themselves at runtime, per their tasks.

What remains optional: the custom machinery the plan originally front-loaded. If you want it — structured traces, a blocking wait, an HTTP state endpoint, a persistent pill — chapter 13 shows the packaged-plugin path with a real installed example as your template.
