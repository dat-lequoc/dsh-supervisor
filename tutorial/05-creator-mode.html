Part I — Foundations

Creator mode and the Cordis toolset

The harness can read and modify itself while it runs — through an agent. This chapter introduces the cordis preset (“创造模式”, Creator mode), walks the seven cordis_* tools it carries, and has you define, run, and remove your first live plugin. Chapter 6 then uses this mode to author your supervisor’s preset.

What Creator mode is

cordis is the fourth shipped preset. Its own header explains its reason to exist better than any summary:

“A person can ask an agent to author another agent” — that is precisely your chapter 6. The preset = standard + three additions:

  • the row tool-cordis (package @deepseek-ai/dsh-tool-cordis) — the toolset;
  • two bundled skills: editing-cordis-compositions (preset authoring) and cordis-plugin-development (dynamic plugins);
  • a persona that teaches the two-plane rule and forbids editing shipped presets.
A docs-drift warning you need before anything else

The comment above says cordis_mount, and the editing-cordis-compositions skill still teaches verbs called cordis_inspect / cordis_mount / cordis_unmount. Those tools no longer exist. The live toolset — read it from the source of truth, packages/extensions/tool-cordis/src/index.ts — registers seven tools with a define/run lifecycle instead. The skill’s advice (planes, copy-then-edit, validation) remains correct; only its tool names are stale. This course always uses the live names below.

The seven tools

Each row cites the registration line in packages/extensions/tool-cordis/src/index.ts:

ToolLineWhat it does
cordis_inspect_list42Lists every inspect provider — read-only query surfaces on host and client — with their methods and schemas. Always your first call.
cordis_inspect_query61Runs one declared read-only query: exact service methods (Service.listService), event contracts (Event.listEvents), sandbox globals (Builtin.listBuiltins), visible tools (Tool.listTools), and — from the browser — live slot trees and theme tokens.
cordis_inspect_self97Lists this session’s dynamic plugins; with pluginId+packageId returns exact source and diagnostics.
cordis_define149Records an immutable package: a name, purpose, and a host half and/or client half of plain-JavaScript code. Validates syntax only — nothing runs yet.
cordis_run241Activates one package (mode: run first time / restart / rollback; update to switch versions). A client half may require your approval in the UI.
cordis_stop330Disposes the running effects; keeps the definition, versions, and grants.
cordis_undefine352Permanently removes the plugin and all its packages.

The vocabulary: Plugin → Package → Run

Three ids, from the toolset’s own system prompt:

So iteration looks like: define v1 → run → find a bug → define v2 under the same pluginId (plugin: {kind: "existing", pluginId}) → run with mode: "update". Rollback is run on the old package. Versions are immutable, so you can always get back.

What dynamic plugins are — and are not

  • They live only in process memory: a dsh restart clears them. They change no file, no cordis.yml, no preset. (README: “Dynamic packages live only in the shared DSH process memory… cannot be promoted automatically.”)
  • They are real: a host half gets a ctx façade onto the live runtime — it can register model tools, listen to events, call services. A client half is delivered to every open web page and can register UI into shipped slots.
  • They are session-scoped: only the session that defined a plugin sees and controls it.
  • The sandbox “isolates globals but is not a security boundary” — hence the shell-access trust stance. (packages/extensions/tool-cordis/README.md, “Trust stance”.)

Perfect, in other words, for probing and prototyping — which is how chapters 6 and 11 use them.

TypeScript corner · why “plain JavaScript”?

Dynamic code is evaluated directly in a node:vm sandbox — no compiler runs. TypeScript annotations would be syntax errors here. This is a feature for you: everything you learned in chapter 2 applies with zero build tooling. When you graduate to a packaged plugin in chapter 13, the same code gains type annotations and a 5-line build script — that’s the whole difference.

Your first live plugin, end to end

Time to drive. Open the web UI → new session → workspace /root/agi-lab → preset 创造模式 / Creator mode (the cordis preset). Then paste each prompt below as a chat message and watch what the agent does. (You are practicing two skills at once: the tool lifecycle, and directing an agent that holds the tools — the same skill your supervisor will need with its workers.)

Step 1 — discover, then query

Prompt 1:
  "Call cordis_inspect_list and tell me, in one line each, which inspect
   providers exist on host and client."

Prompt 2:
  "Using cordis_inspect_query, query host Service.listService with no input
   and show me 10 interesting service keys. Then query the exact service
   'agentPresets' and paste its method signatures."

That second query returns the roster’s real, current signatures — list(), copy(), standingKeyFor() — the exact API chapter 6 scripts against. This discover-before-code discipline is the skill’s standard workflow (steps 1–2), and it is why dynamic plugins rarely guess wrong: the runtime tells you its own contracts.

Step 2 — define a host-half plugin that registers a real model tool

Prompt 3:
  "Define a dynamic plugin (cordis_define, plugin kind 'new', idPrefix 'lab').
   Host half only, with this code, then run it with cordis_run:

   return {
     name: 'lab-uptime',
     apply(ctx) {
       const started = Date.now()
       harness.registerTool(ctx, harness.defineTool({
         name: 'lab_uptime',
         description: 'Seconds since this dynamic plugin was mounted.',
         parameters: {},
         output: {
           schema: { type: 'string' },
           render(_a, v) { return [{ type: 'text', text: v }] },
         },
         async execute() {
           return `up ${Math.round((Date.now() - started) / 1000)}s`
         },
       }))
     },
   }"

Read your own code like a chapter-2 exercise:

  • The function body returns a plugin object — name + apply(ctx) (idea 1).
  • harness is a sandbox builtin (discoverable via Builtin.listBuiltins) whose registerTool/defineTool pair registers a model tool owned by this plugin’s fiber — so cordis_stop removes it (idea 5).
  • parameters: {} and the output block mirror the real ToolDefinition contract from docs/subsystems/tools.md: a schema for the value, a render that turns it into model-visible content.

Step 3 — use it, inspect it, remove it

Prompt 4:  "Call lab_uptime."          → expect: "up Ns"
Prompt 5:  "cordis_inspect_self — show my plugins and their states."
Prompt 6:  "cordis_stop it, try lab_uptime again, and tell me what happens."
           → expect: the tool is gone from the catalog (unknown tool)
Prompt 7:  "cordis_undefine it."
Test it live — milestone: the toolset lifecycle

You pass this chapter when all of these were observed in your Creator session:

  1. cordis_inspect_query returned real signatures for agentPresets.
  2. cordis_define answered with a pluginId/packageId and “not running yet”.
  3. After cordis_run, calling lab_uptime returned an uptime string — a tool that existed nowhere on disk, served by code you wrote into a running process.
  4. After cordis_stop, the tool vanished (effects unwound — chapter 2, idea 5, proven live).
  5. cordis_undefine left cordis_inspect_self reporting no plugins.
Why this matters for the supervisor build

Chapter 6 does not edit files by hand to create your preset — it asks a Creator-mode agent to call ctx.agentPresets.copy() through exactly this define/run mechanism (a temporary probe plugin that registers a preset_* tool, then is undefined). You now know every moving part of that trick. And chapter 11’s optional status pill is a client half registered into a shipped slot — same lifecycle, other side of the wire.

If something goes wrong

  • Run fails technically → have the agent call cordis_inspect_self(pluginId, packageId): it returns the exact source plus the error and stack. Define a corrected package under the same plugin; never overwrite.
  • Client half says “awaiting approval” → that is you: an approval card appears in the conversation. One check mark approves this package; double check marks pre-approve future versions of the same plugin.
  • service "x" is not declared → code used ctx.x without inject; switch to ctx.get('x') or declare it (skill, “Common failure checks”).
