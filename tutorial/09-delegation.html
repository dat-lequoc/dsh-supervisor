Part II — Build · Milestone 4

Workers: spawn, steer, kill, report

The heart of the harness for your purposes: continuable background subagents. This chapter explains the machinery precisely — then you exercise every verb by hand, which is the design’s “M0 smoke test” and the foundation the supervision loop stands on.

What a continuable child actually is

The subagent subsystem doc defines it in one breath worth reading twice:

Unpacked for a supervisor:

  • The child is a real session — a durable logical JSONL log like any other, visible in the web sidebar and inspectable with zstd -dc on disk. Not a throwaway task.
  • “Running” is temporary residency. When the child has turns to execute, an Activation exists; when it finishes and owns nothing, it settles and unloads. The durable session stays.
  • Cold resume is free. Messaging a child whose Activation is gone resurrects it from its persisted session — days later, across process restarts. Your workers are immortal until you choose otherwise.
  • One inbox, with a deliberate steering fast path. Initial tasks and idle/cold follow-ups use the native FIFO. For a running direct child, this bundle's control frontend uses the harness's built-in Agent.steer(), so the correction becomes input to the next model step inside the current turn.

The five verbs and their exact semantics

1 · Spawn

The plugin-owned subagent tool takes { description, prompt, model, run_in_background }. model is required and must be one exact choice from the user-owned Settings → Plugins allowlist. A fresh install enables runtime/current, which explicitly resolves the provider/model captured for the calling request; fixed choices are exact provider/model-id routes. Fixed entries render with native input modalities ([text] / [text,image]), so the supervisor can route image work to a vision-capable worker the user approved. Empty settings disable spawning; no route is inherited implicitly. Each allowed model route owns its effort setting: provider/default omits an explicit effort, while fixed effort ids must be advertised by that selected model. Even runtime/current follows only the main request's model route and never its effort. The tool result displays the effective route, modalities, and effort. The plugin always forwards the resolved route through native SubagentRequest.agentOptions. In background mode it calls ctx.subagents.startContinuable():

Several facts ride along. The child records your supervisor as parentSession in its header (lineage is durable). The row’s persona is registered as the child’s own persona and even snapshotted in its descriptor for cold resume (docs/subsystems/subagent.md: “a continuable descriptor … additionally snapshots resolved child agentOptions.provider/model and optional persona/toolFilter”). And the plugin-owned toolFilter removes ask_user_question, while the child-scoped native report tool remains available. Finally, the tool returns the child id immediately — spawning never blocks on the work. When an explicit effort applies, the plugin reserves that id and writes the effort into the child's first durable request header.

2 · Steer — send_message

The native delivery table still owns idle, waiting, and cold children:

The supervisor preset replaces only the model-facing control row. For a live, running direct child, dsh-supervisor/control calls Agent.steer(), the same primitive used by the web UI's steer action: the message joins at the next model step without waiting for the whole turn. All other states fall through to native followup(). Use interrupt-then-send only when the current turn itself must stop. Direct-parent authority is preserved.

3 · Kill — interrupt_agent + silence

There is deliberately no destroy. Kill = interrupt + never message again: an un-messaged child runs no turns and burns zero tokens, while its session stays on disk for the post-mortem. “Kill” in your changelog means exactly this pair of decisions.

4 · Report — the worker’s side

Every continuable in-process child automatically gets a report tool — your preset didn’t add it; the host row tool-subagent-report registers a continuable-child setup that installs it in every child (packages/bundle/base/cordis.patch.yml, lines 331–333; the cordis preset’s comments explain why that row must be host-plane). Delivery default is wakeup: the parent gets a real turn. That is your blocked-question channel, and your worker persona (chapter 6) already instructs workers to use it. The guarded spawn request also denies the global ask_user_question tool in both schema and execution: a question opened there would wait silently inside the child session and would not emit subagent-report.

5 · The settle notice — the free wake

Unconditional. Every worker you spawn will wake you exactly once when it finishes — with its final message attached. The bundle enriches that same claimed notice from the child's durable final turn/end when retries exhaust, producing text such as Terminal failure [QUOTA]: …. Intermediate retryable failures remain silent; if a retry succeeds, the notice is ordinary. The child remains resumable through send_message.

Bookkeeping — list_agents

Enumerates your children with status running / idle / ready (ready = storage-only, resumable), reading durable state without waking anyone (docs/tool-catalog.md, list_agents; service: listChildren() in subagent.md). This is how the supervisor checks what drivers are open and enforces the settings-owned worker cap. Running is not proof of progress. A check-in must compare a report, artifact/log change, or completed step with the prior NOTES.md checkpoint.

The task prompt: the supervisor’s half of the contract

Native machinery delivers the message; what the message says is your design’s §7.2 structure, now carried entirely in the spawn call (simplification S4 — no brief files). Roles are whatever the mission needs — implementer, browser operator, and notably explorer: a worker whose entire deliverable is a report (survey this repo, map this system), the supervisor’s long-range eyes when its own quick reads aren’t enough. Test it live — the M0 smoke test, by hand

You now drive every verb yourself, as the user, before trusting the supervisor to. Use your main-agent session in $HOME/agi-lab. This is the design’s five-observation M0, adapted to your tools.

Milestone 4 acceptance — five observations

Auto-grade: "$HOME/src/dsh-supervisor/grade-tutorial.sh" m4 — reads the session event logs and verifies all five observations left their durable evidence (spawn/steer/kill calls, the subagent-settled and subagent-report messages, a child report, outcome.md).

  1. Spawn returns an id. Say: “Spawn a dev agent in the background with a slow task: role researcher; objective: sleep 90 seconds using bash, then count files in /tmp; protocol as usual (outcome.md + report).” Expect: the tool result names a started child id; the supervisor’s turn ends. In the sidebar, a new child session appears; on disk, find "$HOME/.dsh/sessions" -name session.jsonl.zstd | wc -l grew by one.
  2. Steer lands at the next step. While the child sleeps, say: “Steer it: also count directories, not just files.” Expect: a send_message call; in the child’s session view, the correction is accepted into the running turn and affects the next model step; the worker need not finish its old plan first.
  3. Settle notice wakes the parent. Wait for the child to finish. Expect: the supervisor wakes on its own with a notice (“how the child ended” + final summary), reads the outcome, and records progress. You did nothing.
  4. Report wakes the parent. Spawn a second worker whose task is deliberately under-specified (e.g. “write the greeting to the configured location” with no location in Context, and an explicit instruction that this is not discoverable — ask via report). Expect: the child calls report with a precise question; the supervisor wakes, answers via send_message; the child completes with the answer as its next turn.
  5. Interrupt stops the burn. Spawn a third worker with a long task, then say: “That one’s off the rails — kill it and log the kill.” Expect: interrupt_agent; list_agents then shows it not running (idle/ready); a kill line lands in CHANGELOG.jsonl; no further child activity appears in its session log.

Also verify the persona took: open the first child’s session in the UI — its behavior should reflect the Dev-Agent persona from your row (e.g. it reports a one-paragraph summary at the end). If the child instead behaves like a generic coding agent and never reports, your persona: block on the dev spawn row (tool-spawn-dev) has an indentation problem — re-validate the preset.

Why observation 2 matters more than it looks

Steering mid-flight is the capability your design originally assumed it would have to build as kill + fork. The small control frontend reuses the harness's existing step-boundary steer primitive, preserving context and leaving idle/cold delivery on the native subsystem.

What exists now

Every mechanical piece of supervision works under your hand: spawn, steer, kill, report, settle, enumerate. What’s left is making the supervisor drive them unattended, on its own clock — the loop.
