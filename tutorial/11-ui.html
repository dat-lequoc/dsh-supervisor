Part II — Build · Milestone 6

UI, the minimal way

Your design sketched two custom tabs. This chapter shows how much of that the shipped web UI already gives you for free, then walks the one piece the bundle now ships — the Feed view tab, a durable client plugin in the native view ring — and keeps the dynamic status pill as an optional exercise in dynamic plugins.

What the shipped UI already is

Map your design’s two tabs onto what’s on screen right now:

So the honest gap is small: a glanceable “what is the supervisor doing right now” view and file-feed convenience. The packaged bundle now closes both with a shipped Feed tab (below); the terminal habit and the dynamic pill remain as alternatives and exercises.

The shipped Feed tab (what the bundle installs)

Since v0.2.0 the dsh-supervisor package ships a durable client plugin: open any session and the view ring (the tabs that hold Chat and Trajectory) gains a Feed entry. For a workspace with an .agi/ directory it renders the whole run at a glance — goal card (live, from the native goal projection), workers with their outcome.md, the progress timeline, the question stack with answered/assumed badges, the action changelog, notes, and the mission report.

  • Browser half — lib/client.js, a hand-written lazy-CJS factory (window.__ModuleLoader__.load…, the format docs/cookbook/adding-a-settings-card.md §Packaging documents). It registers id supervisor-feed into the shipped conversation.view list slot — additive, never replacing Chat. Served automatically by the client-modules scan: the package declares dsh.client {platform:'web'} + exports["./client"], and the page gets /plugins/dsh-supervisor/client.js with no frontend rebuild.
  • Host half — GET /supervisor/feed?ws=<workspace> in lib/index.js: a nested fiber injecting webServer reads the .agi/ tree (text capped, JSONL tail-capped) so headless profiles still mount the preset installer untouched.
  • Data stays native-first — goal from useProjection('goal'), workers from the subagent.list RPC, and only the .agi/ files go through the package's own route.

The meta-config card (Settings → Plugins → Supervisor)

Since v0.4.0 the bundle also ships the supervisor's meta-config through the native settings domain: namespace dsh-supervisor with workerModels (allowlist, with a default Current runtime model dropdown choice plus fixed routes showing native [text]/[text,image] modality tags), maxParallelWorkers (hard-enforced by the spawn tool at call time), wakeMinutes (how often the supervisor wakes to inspect workers), and questionWaitMinutes (how long it waits for an answer before recording an assumption and continuing). Edit it in the UI card or as the dsh-supervisor: block in ~/.dsh/settings.yaml — both are the same revision-fenced document. The model list is the complete policy: the guarded subagent schema exposes only those exact choices, requires one explicitly, and disappears when the list is empty. runtime/current resolves the calling request's captured route, never the stale session-creation route; no implicit fallback exists. Everything applies live: the plugin remounts that schema on model-list changes, revalidates settings on every call, and the SUPERVISOR META-CONFIG system-prompt section is a text function, re-rendered into every request. Two implementation facts worth stealing: a just-spawned continuable child reports activity: 'inactive' until its first turn, so honest cap enforcement needs a starting-ledger on top of the active-count; and the spawn tool declares isConcurrencySafe: false so two same-step spawns serialize through the check.

Optional: a status pill in the shipped overlay slot

Now the flourish — and the excuse to learn client-side dynamic plugins. The web UI’s layout declares a frame-wide floating layer exactly for additions like this:

“A status pill belongs here” — the catalog literally names your use case. The pill will poll your .agi/ files through a package-private host method (harness.handle on the host half, host.call from the client half — the documented RPC bridge from the cordis-plugin-development skill).

In a Creator-mode session (/root/agi-lab), have it first query the slot for real (cordis_inspect_query, client, Slots.listSubTree, root shell.overlay — a browser tab must be open to answer), then define and run this two-halved plugin:

Read your own code against the skill’s rules — every one appears here:

  • Host half exposes one JSON method with harness.handle; client calls it with host.call. Only plain JSON crosses (we parse/slice to scalars first).
  • Client uses React.createElement — no JSX in dynamic code.
  • The timer is the timer service, hard-injected, and ctx.interval returns a disposer that useEffect hands back — teardown-safe on stop/update.
  • The slot is registered inside slots.inject(…), with a fresh id so it adds beside shipped entries, and opts into pointerEvents per the overlay contract.
  • Filesystem access goes through ctx.get('fs') — the Cordis service, not Node globals (which the sandbox withholds). Its read verb is verified: readText(target, signal?) “reads the whole regular text file as one decoded string” (packages/fs/fs/README.md, service table).
Test it live — milestone 6 acceptance

Auto-grade: python3 /root/dev/tests/grade.py m6 — confirms the define/run lifecycle and the inspect-before-code discipline from the Creator session's log; the visuals (steps 2–5) stay yours to judge.

  1. cordis_run returns awaiting-approval for the client half → an approval card appears in the Creator session → approve it once.
  2. The pill appears bottom-right of the web UI, in every open tab.
  3. Append a line and watch it change within ~5 s: echo '{"ts":"now","text":"pill test"}' >> /root/agi-lab/.agi/progress.jsonl
  4. Add a fake pending question line to questions.jsonl → the ❓ counter appears; flip its status to answered → it clears.
  5. cordis_stop → the pill vanishes everywhere (effects unwound, both sides of the wire). Run it again — one approval was enough (the grant persists).

Remember its nature: dynamic plugins die with the process. If you love the pill, chapter 13 explains what “promoting it to a real plugin” involves; until then, re-running it after a restart is two tool calls in any Creator session.

Why we didn’t build the two tabs

A conversation.view tab (the shipped slot for whole view tabs — same catalog, key conversation.view) rendering .agi/ is entirely buildable with exactly the techniques above, and nothing about it is beyond you now. It just isn’t earning its keep: the session list already is the run list, the session view already is the trace, and your files already have a feed. Native-first means spending UI effort only where the shipped surface is actually silent — which turned out to be one pill.
