Part II — Build · Milestone 3

Time: the schedule overlay

A supervisor needs two timers: a patience window on questions and a periodic check-in on running workers. The harness ships both as an opt-in overlay — two rows in your profile patch, hot-applied with no restart. This is your first host-plane change.

What the schedule subsystem is

@deepseek-ai/dsh-schedule owns durable reminders that return to the original session as ordinary later conversation turns. Three facts define the design space (docs/subsystems/schedule.md):

  • Delivery is a turn. A firing reminder is a message into the session’s inbox — the same wake mechanism as everything else in chapter 3. No callbacks, no polling.
  • Three rules: one-shot after_seconds (any positive delay), one-shot absolute at, and recurring every_seconds with a hard minimum of 300 seconds. Records are durable session events, so they survive restarts of the process.
  • Session-local: a reminder returns to the session that created it. Perfect — the Main Agent session is by definition the live one.

Mapping to your two needs:

NeedMechanism
Question patience (questionWaitMinutes, default 5)schedule_create one-shot, after_seconds: questionWaitMinutes*60. No minimum — 2-minute patience works fine.
Periodic worker check-in (wakeMinutes, default 5)schedule_create recurring, every_seconds: wakeMinutes*60 — created when a worker spawns, deleted when work is done. Minimum 300 s ⇒ wakeMinutes ≥ 5, which matches your default.
Why this replaces the plan’s custom wait_for_agents tool (mostly)

The plan’s M2c built a blocking tool: sleep until a child settles or a timeout passes. Natively, both wake sources already exist: a settling child unconditionally delivers a notice to the parent (chapter 9), and the recurring reminder is the timeout. The only difference is form — instead of blocking inside a tool call, the supervisor ends its turn and gets woken. Same loop, zero code. The blocking version remains available as a chapter 13 exercise if you prefer its ergonomics.

The overlay: two rows

Schedule is not mounted by default. The harness ships the opt-in as an example overlay — read it, it is exactly two rows:

  • dsh-schedule — the service, the session driver, and the model tools (schedule_create / schedule_list / schedule_delete).
  • dsh-time-context — injects current time (and the browser’s time zone) into requests, so the model can reason about “in 5 minutes” correctly. Schedule’s doc leans on it for time-zone interpretation; mount them together.

Host plane or preset? Host: the schedule service and driver serve every session and the tools register globally — and more practically, this is the shipped overlay shape. So it goes in your profile patch layer.

Apply it

Back up, then edit your live patch file:

cp /root/.dsh/profiles/web/cordis.patch.yml{,.bak}   # (before editing)
# ... edit ...

No restart: the file is watched, and each change transactionally recomposes the tree (packages/boot/app-boot/README.md: “Every profile boot keeps cordis.patch.yml live through watchUserPatches… A rejected read, parse, or Loader candidate leaves the last good tree running”). If you typo the YAML, the old tree keeps running and the server log (tmux) shows hmr/config-update-failed — fix and save again.

Two sharp edges
  • Duplicate ids are fatal at compose time. If you later add more inserts, never reuse id: schedule etc.
  • An empty patch file must be []. A file of only comments throws (“it parses to nothing, not to a list”) — same README.
Test it live — milestone 3 acceptance
  1. Tools appeared (existing sessions too): in your main-agent session ask “do you now have schedule tools?” — expect schedule_create / schedule_list / schedule_delete in its catalog. (Composition changes reach the live tree; the next turn sees the new tools.)
  2. One-shot delivery: “Create a reminder for 60 seconds from now that says ‘patience-test’. Then stop.” Wait a minute doing nothing. Expect: the agent wakes by itself with a new turn carrying the reminder — you see it arrive in the conversation.
  3. The persona’s patience path now works: re-run chapter 7’s question test — ask it something ambiguous mid-work, stay silent. With questionWaitMinutes: 2 in your config.json, expect: question logged as pending → reminder created → two minutes later it wakes, flips the entry to assumed with a recorded assumption, logs it, and proceeds.
  4. Recurring floor: “create a recurring reminder every 60 seconds” — expect a refusal/error (minimum 300 s), proving you know where the floor is.
TypeScript corner · reading the schedule record types

docs/subsystems/schedule.md defines the durable records as interfaces — e.g. interface AfterScheduleRecord { readonly kind: 'after'; readonly afterSeconds: number; … }. Two idioms to bank: a literal type (kind: 'after' — the field can only ever be that exact string; unions of these make “tagged unions” you can switch on), and readonly (compile-time immutability). Durable records here are tagged unions everywhere: events, stop reasons, message sources. Recognizing the tag field is half of reading harness types.

What exists now

A supervisor that can wake itself. The question protocol is fully operational; the periodic check-in has its mechanism but nothing to check on yet. Next: workers.
