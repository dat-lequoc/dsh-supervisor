Part II — Build · Milestone 1

Author the main-agent preset

Your supervisor is born as a preset: a copy of standard with its own name, description, and (next chapter) persona. This chapter creates it through the roster, validates the mount, adds a dedicated worker-spawning row, and starts your first session on it.

The plan for this milestone

  1. Use a Creator-mode agent to call ctx.agentPresets.copy('standard', 'main-agent', …).
  2. Fix the copy’s preset.yml metadata.
  3. Add one row: a second delegation tool spawn_dev_agent with a worker persona — reusing the shipped dsh-tool-subagent plugin, zero custom code.
  4. Mount-validate with standingKeyFor('main-agent').
  5. Start a session on it and inspect its tool list.
Why a second tool-subagent row instead of a custom spawn plugin

Your design’s amendment A6 planned a custom agi-spawn plugin so each spawn could carry its own persona. Native-first observation: the shipped row config already supports a per-row persona, toolFilter, and agentOptions (provider/model) (docs/config-catalog.md, §dsh-tool-subagent). One persona per row is less flexible than one per spawn — but the per-spawn part (“you are a browser operator”, “you are a researcher”) travels perfectly well in the task prompt itself. So: shipped plugin, dedicated row, role in the prompt. If you ever outgrow this, chapter 13 shows the custom tool.

Step 3 — add the worker-spawning row

Open /root/.dsh/.agent-presets/main-agent/agent.cordis.yml. Find the delegation group (you read it in chapter 2 — it already carries tool-subagent-control, tool-subagent, and friends). Inside that same group’s config list, add one more row:

Why each field, with the receipts:

  • provider: spawn — the in-process backend that creates a fresh child (no parent history). Registered host-side by subagent-spawn-in-process (packages/bundle/base/cordis.patch.yml, lines 295–298).
  • toolName: spawn_dev_agent — your supervisor gets a tool by this name, distinct from the generic subagent tool it also keeps.
  • backgroundMode: continuable — children are durable sessions you can send_message / interrupt_agent, and whose settling wakes the parent. (Chapter 9 is entirely about this.)
  • persona — registered as the child’s persona, shadowing the deployment default for that child alone. This is the documented per-request persona path: “in-process backends … register it as a scoped deployment:persona section on the child” (docs/subsystems/subagent.md, SubagentStartRequest.persona).

Optionally, pin the worker model on the same row (this is where your design’s subagentModel knob lives now — user-owned YAML, not agent-editable): 

        agentOptions:
          provider: deepseek-official     # match your deployment's route names
          model: deepseek-chat            # check Settings → Models in the web UI
Do not add agi-* service rows here

Everything else this build needs is host-plane (schedule, chapter 8) or already present. A service row loose in a preset is the classic mount rejection from chapters 2–3. The delegation group you are editing already has the right realm (isolate: workflowEngine) for what it owns.

Step 4 — validate the mount

Back in your Creator-mode session (same probe-plugin trick — or just ask it; it remembers the pattern):

standingKeyFor is the real check — it composes the preset’s subtree exactly as a session start would. The four failure shapes it can name, and what each means:

RejectionMeaningFix
Cannot find package …A row names a package this deployment doesn’t have.Typo in name:, or the plugin needs installing (chapter 13’s topic).
invalid config: $.<field> …Row config fails the plugin’s schema.Fix the named field. (E.g. a typo in backgroundMode.)
N row(s) did not activate: waiting for <service>A consumer can’t resolve a service.You put a consumer inside the wrong realm, or the host lacks the service.
published process-global service(s) […] / service "x" has been registeredThe realm rule violation.Wrap provider+consumers in an isolate group — or the row belongs host-side.

Source for the list: editing-cordis-compositions skill, “Verifying a change”. Note its other warning: the roster’s broken flag is only a file-shape check — not validation.

Step 5 — first session on your preset

Web UI → new session → workspace /root/agi-lab → preset picker now shows Main Agent (Supervisor) under your custom presets. Start it, then ask it: 

"List every tool you can currently call, names only, grouped by theme."
Test it live — milestone 1 acceptance
  1. standingKeyFor('main-agent') returned clean (“mounted OK” or equivalent — no thrown error).
  2. The preset appears in the picker with your display name and description.
  3. The new session’s tool list contains, at minimum: spawn_dev_agent, subagent, send_message, interrupt_agent, list_agents, goal-related tools, todo_write, plus the ordinary bash/fs suite.
  4. Negative check: a second session on main-agent starts cleanly too (proves you didn’t introduce a realm collision).

If spawn_dev_agent is missing: your row is outside the delegation group’s config: list (indentation!), or the file didn’t save. Re-run step 4 — the validator’s message will name the row.

TypeScript corner · reading the row’s config schema

How did we know persona and agentOptions are legal fields? The plugin declares a Config schema, and the generated catalog renders it: /root/deepseek-harness/docs/config-catalog.md, section dsh-tool-subagent. When you wonder “what can this row take?”, the catalog is the answer — and invalid fields fail loud at validation, never silently.

A supervisor-shaped agent: right tools, right delegation row, no brain yet — its persona is still standard’s generic coding text. Chapter 7 writes the brain.
