Part II — Build · Milestone 1

Author the main-agent preset

Your supervisor is born as a preset: a copy of standard with its own name, description, and (next chapter) persona. This chapter creates it through the roster, validates the mount, adds a dedicated worker-spawning row, and starts your first session on it.

The plan for this milestone

  1. Use a Creator-mode agent to call ctx.agentPresets.copy('standard', 'main-agent', …).
  2. Fix the copy’s preset.yml metadata.
  3. Replace the native spawn frontend with one plugin-owned subagent row carrying the worker persona and settings-only model policy.
  4. Mount-validate with standingKeyFor('main-agent').
  5. Start a session on it and inspect its tool list.
Why the plugin owns the one subagent frontend

The shipped frontend is excellent at lifecycle management, but its model-facing schema has no model argument. Its child therefore inherits the parent agent's creation-time route, which can be stale after live model selection changes. That also bypasses the Supervisor card's allowlist. dsh-supervisor/spawn keeps the same native spawn backend and continuable child sessions, while requiring an explicit choice from live settings and forwarding the resolved route through native SubagentRequest.agentOptions. Fixed choices are exact provider/model ids; runtime/current safely follows the route captured for the calling turn. It is mounted as subagent, replacing — not sitting beside — the native spawn row. The protocol persona remains per row; the task role (“browser operator”, “researcher”) travels in the prompt's # Role section.

Why each field, with the receipts:

  • provider: spawn — the in-process backend that creates a fresh child (no parent history). Registered host-side by subagent-spawn-in-process (packages/bundle/base/cordis.patch.yml, lines 295–298).
  • toolName: subagent — the canonical name now refers only to the plugin-owned guarded frontend. Do not keep the shipped spawn row beside it.
  • The plugin always uses continuable mode — children are durable sessions you can send_message / interrupt_agent, and whose settling wakes the parent. (Chapter 9 is entirely about this.)
  • persona — registered as the child’s persona, shadowing the deployment default for that child alone. This is the documented per-request persona path: “in-process backends … register it as a scoped deployment:persona section on the child” (docs/subsystems/subagent.md, SubagentStartRequest.persona).

Choose worker models in Settings → Plugins → Supervisor. A fresh install enables Current runtime model (runtime/current) in that list. The generated subagent.model enum contains only enabled choices, and an empty list disables spawning.

Do not add agi-* service rows here

Everything else this build needs is host-plane (schedule, chapter 8) or already present. A service row loose in a preset is the classic mount rejection from chapters 2–3. The delegation group you are editing already has the right realm (isolate: workflowEngine) for what it owns.

Web UI → new session → workspace /root/agi-lab → preset picker now shows Main Agent (Supervisor) under your custom presets. Start it, then ask it:

Test it live — milestone 1 acceptance

Auto-grade: python3 /root/dev/tests/grade.py m1 — checks the preset files, the guarded subagent row (fields, worker persona, group placement), absence of the native fallback row, and that sessions mounted.

  1. standingKeyFor('main-agent') returned clean (“mounted OK” or equivalent — no thrown error).
  2. The preset appears in the picker with your display name and description.
  3. The new session’s tool list contains, at minimum: subagent, send_message, interrupt_agent, list_agents, goal-related tools, todo_write, plus the ordinary bash/fs suite.
  4. Negative check: a second session on main-agent starts cleanly too (proves you didn’t introduce a realm collision).

If subagent is missing: first confirm at least one Worker model is saved in Settings → Plugins → Supervisor. Then check that the replacement row is inside the delegation group's config: list (indentation!) and re-run step 4.

TypeScript corner · reading the row’s config schema

The replacement plugin declares its row Config with Schemastery and generates a separate model-facing schema with defineTool. This distinction is important: row config chooses the backend and persona, while the live Settings allowlist determines the required model enum shown to the agent. For runtime/current, execution reads the calling request's logged route—not the agent's creation-time defaults. Invalid row fields fail during composition; removed choices fail again at execution time.
