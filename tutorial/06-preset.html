Part II — Build · Milestone 1

Install and inspect main-agent

This is the first build action. You install the repository as a dsh profile bundle, restart once, and let its non-destructive setup plugin install the exact current preset. Only after the package exists do you inspect rows named dsh-supervisor/….

The dependency order

clone repository                         (setup page)
  → dsh plugin add                      (package becomes profile dependency)
    → restart dsh web                   (bundle rows compose at boot)
      → setup plugin installs preset    (main-agent appears)
        → preset subpath rows resolve   (goal/control/spawn mount)
          → start and test a session

Reversing the middle two steps produces the exact error this chapter is designed to prevent: Cannot find package dsh-supervisor/control or dsh-supervisor/spawn. A YAML row is not an npm installation instruction; its package must already resolve from the profile.

Step 1 — confirm the clean preflight

test -f "$HOME/src/dsh-supervisor/package.json"
test -f "$HOME/src/dsh-supervisor/agent-presets/main-agent/agent.cordis.yml"
test -f "$HOME/.dsh/profiles/web/package.json"

# On the clean course path this should print no supervisor dependency yet:
grep -n 'dsh-supervisor' "$HOME/.dsh/profiles/web/package.json" || true

If $HOME/.dsh/.agent-presets/main-agent already exists on a machine that is not actually clean, move it aside before installing if you want the package's current preset. The installer never clobbers a user-owned preset in its default syncPreset: if-absent mode.

Step 2 — install the supervisor bundle

cd "$HOME/src/dsh-supervisor"
dsh plugin --profile web add "file:$PWD"

This one command updates the profile dependency and ordered bundle list. Do not run npm install inside the dsh profile and do not hand-edit its package.json. The package manager may print peer-dependency warnings because Harness supplies those peers from its own installation; use the installation gate below to distinguish a harmless warning from failure.

Return to the terminal running dsh web, press Ctrl-C, wait for shutdown, then run: 

dsh web

The restart is required because bundle lists compose at boot. During boot, this package mounts its settings/feed host plugin and the native schedule service, then copies the packaged main-agent directory into $HOME/.dsh/.agent-presets/ because it is absent.

Step 3 — prove package, bundle, and preset all exist

Installation gate 
grep -n 'dsh-supervisor' "$HOME/.dsh/profiles/web/package.json"
dsh --profile web --dump-config | grep -E 'agi-schedule|agi-supervisor-setup'
test -f "$HOME/.dsh/.agent-presets/main-agent/agent.cordis.yml"
test -f "$HOME/.dsh/.agent-presets/main-agent/preset.yml"

All four commands must succeed. In the browser, Settings → Plugins must also contain Supervisor. Stop here if any check fails.

Step 4 — inspect the rows the package installed

Open $HOME/.dsh/.agent-presets/main-agent/agent.cordis.yml read-only. The important policy substitutions are already complete:

Now verify the bypasses are absent:

grep -nE 'subagent_fork|@deepseek-ai/dsh-tool-goal' \
  "$HOME/.dsh/.agent-presets/main-agent/agent.cordis.yml" || true

The command should print nothing. The package exports that make the three custom names resolvable are visible in $HOME/src/dsh-supervisor/package.json as ./goal, ./control, and ./spawn. Their lifecycle backends remain native; these frontends add grounded goals, next-step steering, and settings-owned model/effort policy.

Step 5 — mount a real session

Web UI → new session → workspace $HOME/agi-lab → preset Main Agent (Supervisor). Start it and ask: 

List every tool you can currently call, names only, grouped by theme.
Milestone 1 acceptance

Auto-grade: "$HOME/src/dsh-supervisor/tutorial/grade.sh" m1 --ws "$HOME/agi-lab"

  1. The session starts with no Cannot find package mount error.
  2. Tools include subagent, send_message, interrupt_agent, list_agents, get_goal, start_goal, and update_goal.
  3. subagent_fork and native create_goal are absent.
  4. A second session on the same preset also starts, proving no preset service leaked into the process-global realm.
Where preset authoring still fits

Chapters 2–5 taught enough Cordis and roster mechanics to author a variant. For the primary course, using the packaged preset is the reproducible build: it cannot drift from the plugin version that supplies its rows. If you create a variant later, copy main-agent to a new id through the roster, edit that user copy, and mount-validate it with standingKeyFor.

What exists now

A fully mountable supervisor preset, its package-owned policy frontends, live settings, Feed routes, and schedule service. Chapter 7 reads and tests the installed persona and durable state contract.
