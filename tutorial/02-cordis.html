Part I — Foundations

Cordis from scratch

The harness’s slogan is “everything is a plugin.” This chapter teaches the plugin framework underneath — Cordis — well enough that when you later read a real plugin, every line means something. It also quietly teaches you the JavaScript and TypeScript you need along the way.

Why a plugin framework at all?

Imagine building an AI agent product the ordinary way: a big program where the model client, the tool registry, the session log, and the UI all import each other. Every new capability means editing the core. DeepSeek Harness refuses that: there is no privileged core to patch. The model adapter is a plugin. The tool registry is a plugin. The agent loop itself is a plugin. You extend the product by mounting another plugin beside the others, and you remove your extension by unmounting it — nothing else changes.

Cordis is the framework that makes this composable. The harness vendors it (a pinned copy lives at /root/deepseek-harness/vendor/cordis/), and its primer condenses the whole thing into five ideas. Here they are, verbatim from the harness docs, then unpacked one by one:

Idea 1 — A plugin is a small object with an apply function

Here is the smallest possible plugin, in plain JavaScript:

That’s it. A plugin is a module (or object) exposing a name and an apply function. When the framework mounts the plugin, it calls apply(ctx) exactly once, handing it a context — the plugin’s window into everything else. When the plugin is unmounted, everything it registered through that context is automatically torn down (idea 5 explains how).

TypeScript corner · reading export, const, function

JavaScript files are modules: export marks what other files may import. const declares a variable that cannot be reassigned. TypeScript is JavaScript plus type annotations — notes about what shape a value has, checked before the code runs and then erased. The same plugin in the harness’s own TypeScript style looks like: 

export function apply(ctx: Context): void { ... }

Read ctx: Context as “ctx is a Context” and : void as “returns nothing.” When you skim harness source, you can mentally delete everything after a colon in a parameter list and still understand the runtime behavior.

Idea 2 — A context is a repository of services

A service is a long-lived object that claims a stable key on the context. The tool registry claims ctx.tools; the session store claims ctx.sessions; the subagent runtime claims ctx.subagents. Any plugin can then reach a capability by key, without importing (or even knowing) the package that implements it:

This indirection is what makes providers swappable. The filesystem service, the shell service, the subagent providers — each is “whoever registered under this key.” Point the keys at a remote sandbox implementation and the whole product moves there, no callers edited. The harness architecture doc calls a swappable capability like this a seam (docs/architecture.md, “Capability seams”).

Idea 3 — inject: declaring dependencies instead of ordering boot

What if your plugin requires a service? You could call ctx.get() and hope it’s there — but load order would then matter, and with hundreds of plugins that is unmanageable. Instead a plugin declares its requirements:

A plugin naming services in inject simply waits — Cordis keeps it pending until every named service exists, then activates it. If a service later disappears (its provider unmounts), dependents are deactivated. Load order becomes a property the framework computes, not something you sequence by hand. This is also your first debugging lever: a plugin that “never ran” is usually a plugin waiting on a service nobody provides, and the harness reports exactly that (“N row(s) did not activate: waiting for <service>” — you will meet this message in chapter 6’s validation step).

TypeScript corner · arrays and strings

['tools', 'systemPrompt'] is an array literal of strings. TypeScript infers its type as string[] (“array of strings”). You will also see readonly string[] — same thing, but the compiler forbids mutating it. Neither annotation exists at runtime.

Idea 4 — Typed events, and the four dispatch modes

Services expose methods for direct calls (“start a subagent”), and events for interception and observation (“a tool is about to execute”). A plugin listens with ctx.on(name, listener). What makes Cordis events unusual is that every event declares a dispatch mode — part of its public contract:

  • emit — fire-and-forget observation. Example: session/event, the firehose that announces every appended session-log event. Listeners can watch; they cannot change anything.
  • waterfall — around-middleware. Each listener receives the arguments plus a next function and wraps the rest of the chain. This is how policy is written: the tool pipeline’s tools/pre-execute is a waterfall where a listener can allow, deny, delay, or transform a tool call.
  • parallel / serial — awaited fan-out, in parallel or in order.
The waterfall rule that catches everyone

A waterfall listener must call and return next() to delegate. Returning without it short-circuits the chain — deliberately when a policy owns the decision, catastrophically when you just forgot. The harness conventions state it in bold (AGENTS.md: “Waterfall listeners MUST call next()”). A dropped next() on tools/pre-execute silently blocks every tool in the process. Burn this in now; it will matter if you build chapter 13’s delay plugin. 

ctx.on('some/waterfall', (payload, next) => {
  // observe or annotate payload here ...
  return next()            // ← the load-bearing line
})
TypeScript corner · arrow functions and callbacks

(payload, next) => { ... } is an arrow function — a compact anonymous function. JavaScript passes functions around like values, so “register a listener” literally means “hand this function to ctx.on, to be called later.” async before a function makes it return a promise (a value that arrives later); inside one, await expr pauses until expr resolves. You will see async execute(args, exec) { ... await ... } in every tool definition.

Idea 5 — Registrations are reversible effects

Here is the question that makes or breaks a hot-reloadable system: when a plugin unmounts, how does the framework undo everything it did? Cordis’s answer: every contribution goes through the context, and every one returns (or is wrapped in) a disposer — a cleanup function. Registering and cleaning up are one act:

The repo states the convention as a hard rule: “Registrations are effects: every contribution goes through ctx.effect() / ctx.on(); a registry’s register() returns the disposer” (/root/deepseek-harness/AGENTS.md, Conventions).

Composition: plugins are mounted from YAML

So far, plugins in isolation. Who decides which plugins run? In this harness: configuration files, not code. A cordis.yml is a list of rows, each naming a plugin package and its config. Here are two real rows from the preset you will copy in chapter 6:

Reading a row:

  • id — the row’s stable address. Patches (next chapter) target rows by id.
  • name — the npm package whose plugin gets mounted.
  • config — passed to the plugin, validated against its schema. Invalid config fails loud at mount.
  • disabled: !!js … — the one place executable expressions are allowed: !!js lets a row switch on the environment (here: skip bash on Windows). Everything else in the file is literal data.
  • {{model}}, {{cwd}} — template variables some plugins (like the persona) resolve per-agent.

This is the deepest thing to understand about the harness: changing what an agent can do means changing which rows are composed for it. Not editing core code — editing a list. The editing-cordis-compositions skill that ships with Creator mode opens with exactly that sentence (apps/cli/config/agent-presets/cordis/skills/editing-cordis-compositions/SKILL.md).

Groups and isolate realms (the collision rule, previewed)

One more composition construct you will see in chapter 6: rows can be nested in a group, and a group can carry an isolate realm. Why: some plugins provide a service, and a service key registers once per realm. If a preset row provided a service into the global realm, the second session mounting that preset would collide with the first. So a preset that owns a service wraps the provider and its consumers in a group with isolate: {thatService: true}, giving each session a private instance. But you must recognize the pattern, because the mount validator will name it when something is wrong (“a preset service must sit behind an isolate realm or move to the host composition”), and chapter 6 teaches you to read that rejection.

Check your understanding (no machine needed)
  1. A plugin’s apply never ran and the mount report says “waiting for schedule.” What is wrong, and why is it not a bug in the plugin? (It declared inject: ['schedule'] and nothing in the composition provides that service — the fix is a composition change, not a code change.)
  2. A tools/pre-execute listener logs every call and then returns nothing. What breaks? (Every tool call in the process silently stops — the listener short-circuited the waterfall by not returning next().)
  3. Why does a preset row providing a service need an isolate realm? (A service registers once per realm; two sessions mounting the preset would collide in the global realm.)
