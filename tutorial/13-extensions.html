Part III — Beyond native

Optional extensions: real host plugins

Everything the plan’s M2 wanted — a tool-call delay, per-worker trace files, a blocking wait_for_agents, an HTTP state endpoint — as packaged, restart-surviving plugins installed into your profile. You may never need them; when you do, this is the honest path, with a real installed plugin as your template.

When to reach for this chapter

  • You want a capability to survive restarts (dynamic plugins die with the process).
  • You want it process-wide — observing every session, or serving HTTP.
  • You have prototyped it dynamically (chapters 5/11) and it earned permanence.

The rule of thumb from the toolset’s own docs: dynamic packages “cannot be promoted automatically. To keep an experiment, implement a normal … plugin through the regular development workflow” (packages/extensions/tool-cordis/README.md). This chapter is that workflow.

This repo already uses the pattern

The supervisor project itself is packaged this way: /root/dev/package.json declares dsh.bundle.patch, its cordis.patch.yml inserts the schedule rows plus a setup plugin (lib/index.js, plain ESM, no build step) that installs the bundled main-agent preset into the user preset root at boot — verified end-to-end: dsh plugin --profile web add file:/root/dev registered the dependency and the bundles entry, and a restart from a deleted-preset state auto-installed everything. Read those three files as the minimal worked example before building agi-extras below; note that a plugin whose job is a filesystem installation (not a runtime registration) legitimately has nothing to dispose.

Your template ships with your machine

/root/dsh-subagent-agy is a working out-of-tree plugin already installed into your web profile — you saw its wiring in chapter 3. Anatomy:

The recipe, extracted:

  1. An npm package ("type": "module", built JS in lib/, source in src/).
  2. Harness packages as peer dependencies — you compile against them; the running dsh provides them (chapter 3: profile module resolution makes bare names resolve to the install).
  3. A one-row cordis.patch.yml + the dsh.bundle manifest field → the package is a bundle: listing it in the profile’s dsh.profile.bundles mounts its rows as one more layer.
  4. Install = add to the profile’s package.json ("file:/root/my-plugin" under dependencies, name under bundles), run the profile’s package manager install, restart dsh once. (The comment shows the porcelain path too: dsh plugin add ….)
TypeScript corner · the build step, demystified

A packaged plugin is TypeScript in src/, compiled once to plain JS in lib/ — look at scripts/build.sh in the template; it is a handful of lines around tsc. Everything you wrote dynamically in chapters 5/11 becomes valid TypeScript by adding types at the edges: import type { Context } from '@deepseek-ai/cordis' and apply(ctx: Context). Start by copying the template’s tsconfig.json and build script verbatim.

Scaffold: agi-extras, one package, four small plugins

Rather than four packages, make one — /root/agi-extras — whose bundle patch inserts a row per feature (each row addressable, hence individually disable-able from your profile patch):

Below, each plugin’s core — adapted from your plan’s skeletons, corrected against the docs you now know. Each carries its verification pointer; honor the plan’s own rule: read the referenced doc before finalizing a signature — never guess.

1 · agi-tool-delay — the waterfall lesson, applied

The listener signature is verified, not guessed: 'tools/pre-execute'(exec: ToolExecution, next: () => Promise<PreToolDecision>) — a waterfall whose listeners return an allow/deny/ask decision, where “next() delegates to allow” (docs/subsystems/tools.md, line 693). Delay-then-delegate is therefore just an awaited pause before returning next().

3 · agi-wait — wait_for_agents, if you prefer blocking ergonomics

Uses two verified contracts: defineTool (chapter 5; full reference docs/subsystems/tools.md) and ctx.subagents.listChildren(parentSessionId, signal?), whose entries are a tagged union — child rows are { kind: 'child', id, activity: 'running' | 'inactive', … } and damaged siblings arrive as { kind: 'diagnostic', id, reason } rows without an activity field (packages/subagent/subagent/src/list-children.ts, lines 44–57 — so every read of activity must check kind first). One caution from your plan stands: the base mounts dsh-tool-call-timeout-policy, so either configure its row above your wake interval or return early with “call me again.”

Plane note: registering into the host tools registry from a host plugin makes the tool visible everywhere. If you want it supervisor-only, keep the host plugin providing nothing and add a preset row instead — or accept global visibility; it is harmless to agents without children.

4 · agi-state-route — .agi/ over HTTP

The supervisor bundle already ships the bounded GET /supervisor/feed?ws=… route used by Feed. Treat this sketch as a lesson for a different mission-specific schema, not something the current supervisor still needs. The route contract is exactly chapter 3’s web server: ctx.webServer.register({ kind, path, handler }) returns a disposer; duplicates throw (docs/subsystems/web-server.md). Path-validate the ws query parameter — the server is unauthenticated localhost.

Install into the profile

Bundle layers are boot-time

Unlike your live-watched patch file, the bundle list composes at boot — hence the one restart. Afterwards, iteration is: rebuild lib/, restart. (Compare the antigravity plugin’s own README/scripts for its selftest habits — a good pattern to copy.) To disable one feature without uninstalling, add an id-targeted disabled: true patch for its row in your profile patch — that part is live.

Test it live — per plugin
  1. delay: set "toolDelaySeconds": 2 in the lab’s config; a tool call in a .agi-workspace session visibly lags ~2 s (compare tool/call→tool/result timestamps in the session log); a session elsewhere doesn’t.
  2. trace: spawn any worker; .agi/subagents/<id>/trace.log fills with one line per child tool call.
  3. wait: in the supervisor: “spawn a 60-second sleeper, then call wait_for_agents” — returns early on settle; with a long child, returns at wakeMinutes.
  4. state: curl -s 'http://127.0.0.1:3080/agi/state?ws=/root/agi-lab' | python3 -m json.tool
  5. teardown proof: disable a row via profile patch → its capability vanishes without a rebuild (effects unwound — chapter 2, idea 5, at packaged scale).

Survey: how the ecosystem packages presets

The dsh-plugin GitHub topic is the official discovery channel, and community aggregators (awesome-lists with auto-refreshed indexes; visual marketplaces like WhaleHub) build directly on it. Cloning the preset-shipping plugins in that index shows three distribution shapes, all live in the wild:

ShapeExampleMechanics
Script-onlydsh-preset-qa-modePreset directory + install.sh/.ps1 copying into ~/.dsh/.agent-presets/. No package, no bundle. (= this repo’s scripts/install-manual.sh fallback.)
Bundle with a copy-at-boot installerdsh-minimal-msys2, and this repodsh.bundle.patch inserts one plugin row; the plugin materializes packaged presets into the user preset root if absent. Discovery is unmemoized, so no restart is needed after the copy; uninstalling the plugin deliberately leaves installed presets alone. Use ctx.logger, not console.
Bundle registering packaged assets as rootsdsh-preset-scaffoldInstead of (only) a preset, its plugin registers the package’s own skills/ directory as a skill root via FileSystemSkillProvider (includeDefaultRoots: false, customSkillDirs) — its guidance loads into every session on the host profile with no preset switch. A pattern worth stealing when your contribution is knowledge, not composition.

Also seen: the roster supports deployment-configured extra preset roots (dsh-agent-presets Config), but a bundle patch cannot append to the shipped row’s config without restating it wholesale — which is why copy-at-boot won in practice. For monorepos there is a subpath install form: github:owner/repo#ref&path:/.dsh-plugin.

Packaged client plugins (last word on UI)

The repository now contains the concrete production example this chapter once lacked: lib/client.js registers the durable Feed and Supervisor settings card, while lib/index.js supplies their host routes. package.json declares dsh.client.platform: web and exports ./client, so the harness's client-module scan serves it without rebuilding the core frontend. Copy that pattern only when your new surface earns a permanent packaged seat; use chapter 11's retired pill exercise for disposable experiments.
