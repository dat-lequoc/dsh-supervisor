Part III — Beyond native

Optional extensions: real host plugins

Everything the plan’s M2 wanted — a tool-call delay, per-worker trace files, a blocking wait_for_agents, an HTTP state endpoint — as packaged, restart-surviving plugins installed into your profile. You may never need them; when you do, this is the honest path, with a real installed plugin as your template.

When to reach for this chapter

  • You want a capability to survive restarts (dynamic plugins die with the process).
  • You want it process-wide — observing every session, or serving HTTP.
  • You have prototyped it dynamically (chapters 5/11) and it earned permanence.

The rule of thumb from the toolset’s own docs: dynamic packages “cannot be promoted automatically. To keep an experiment, implement a normal … plugin through the regular development workflow” (packages/extensions/tool-cordis/README.md). This chapter is that workflow.

Your template ships with your machine

/root/dsh-subagent-agy is a working out-of-tree plugin already installed into your web profile — you saw its wiring in chapter 3. Anatomy:

The recipe, extracted:

  1. An npm package ("type": "module", built JS in lib/, source in src/).
  2. Harness packages as peer dependencies — you compile against them; the running dsh provides them (chapter 3: profile module resolution makes bare names resolve to the install).
  3. A one-row cordis.patch.yml + the dsh.bundle manifest field → the package is a bundle: listing it in the profile’s dsh.profile.bundles mounts its rows as one more layer.
  4. Install = add to the profile’s package.json ("file:/root/my-plugin" under dependencies, name under bundles), run the profile’s package manager install, restart dsh once. (The comment shows the porcelain path too: dsh plugin add ….)
TypeScript corner · the build step, demystified

A packaged plugin is TypeScript in src/, compiled once to plain JS in lib/ — look at scripts/build.sh in the template; it is a handful of lines around tsc. Everything you wrote dynamically in chapters 5/11 becomes valid TypeScript by adding types at the edges: import type { Context } from '@deepseek-ai/cordis' and apply(ctx: Context). Start by copying the template’s tsconfig.json and build script verbatim.

Install into the profile

Bundle layers are boot-time

Unlike your live-watched patch file, the bundle list composes at boot — hence the one restart. Afterwards, iteration is: rebuild lib/, restart. (Compare the antigravity plugin’s own README/scripts for its selftest habits — a good pattern to copy.) To disable one feature without uninstalling, add an id-targeted disabled: true patch for its row in your profile patch — that part is live.

Test it live — per plugin
  1. delay: set "toolDelaySeconds": 2 in the lab’s config; a tool call in a .agi-workspace session visibly lags ~2 s (compare tool/call→tool/result timestamps in the session log); a session elsewhere doesn’t.
  2. trace: spawn any worker; .agi/subagents/<id>/trace.log fills with one line per child tool call.
  3. wait: in the supervisor: “spawn a 60-second sleeper, then call wait_for_agents” — returns early on settle; with a long child, returns at wakeMinutes.
  4. state: curl -s 'http://127.0.0.1:3080/agi/state?ws=/root/agi-lab' | python3 -m json.tool
  5. teardown proof: disable a row via profile patch → its capability vanishes without a rebuild (effects unwound — chapter 2, idea 5, at packaged scale).

Promoting the pill (last word on UI)

A client half in a packaged plugin is where real frontend tooling begins (the shipped UI plugins are dual-face packages with a bundling pipeline — see any packages/client/ui-*). Before walking that road, remember the pill costs two tool calls to re-run after a restart — and a Creator-mode agent can be asked to do that. For a 24/7 system, “the supervisor re-runs its own pill on boot” is a perfectly good persona line; full client packaging is rarely worth it for one overlay div.
